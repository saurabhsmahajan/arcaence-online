# Decision log

One row per decision. Revisit a row when its "revisit when" condition happens.

| ID | Date | Decision | Alternatives | Why | Trade-off | Revisit when |
|---|---|---|---|---|---|---|
| 001 | 2026-11-11 | Separate repo `arcaence-online` as the base project | Keep inside `arcaence-labs` | Later layers (evals, security, governance, AWS) build on one codebase | Early proof commits stay in `arcaence-labs` | Never expected |
| 002 | 2026-11-11 | RAG is a fixed workflow, not an agent | Agentic retrieval loop | Predictable, testable, cheaper; agents only where they earn it (the desk) | Less flexible on odd questions | Golden set shows retrieval misses a loop would fix |
| 003 | 2026-11-11 | Postgres with pgvector in Supabase | Dedicated vector database | One store for vectors, metadata filters, customer tables and row-level security | Less tuning headroom at large scale | Corpus grows past what one Postgres handles well |
| 004 | 2026-11-11 | Index every document with a `status`; filter at retrieval | Index approved documents only | Tests can run with the filter on and off to show which control catches which trap | Bad chunks sit in the database, so the filter must be tested | Never expected |
| 005 | 2026-11-11 | Local embeddings with fastembed | Hosted embedding API; sentence-transformers | No per-call cost, runs offline, no PyTorch install | Smaller model, lower quality ceiling | Retrieval recall is the bottleneck |
| 006 | 2026-11-11 | Stable semantic clause IDs via a registry | Cite raw section numbers | Numbers shift between v2 and v3 (downgrades is 3.6 then 3.7) | Registry must be maintained | Never expected |
| 007 | 2026-11-11 | Supabase session pooler connection | Direct connection | Direct is IPv6 only on the free plan | Pooler has its own limits | Moving to a paid plan or AWS |
| 008 | 2026-11-11 | Golden set and traps written before code | Write tests after the pipeline | Prevents grading our own homework | Some questions will need revising | Phase 3 expands the set |
| 009 | 2026-11-11 | Status and authority rank come from an explicit manifest, not inferred from text | Let the loader or the model classify documents | A draft that says "approved" can't fool a manifest; a person reviews it in git | Someone must update it when a file is added | The corpus grows beyond hand-maintained size |
| 010 | 2026-11-12 | Skip hidden sheets and tracked deletions | Extract everything and filter later | A person does not see them, so the bot must not quote them | The removed content is not auditable unless we log it | We need an audit of what was removed |
| 011 | 2026-11-12 | Prices come only from the `plans_fees` table, never from extracted or OCR text | Take prices from extracted or OCR text | Extraction is approximate. Money must be exact | Two sources to keep in step | Pricing becomes complex enough for a pricing service |
| 012 | 2026-11-12 | Stop OCR tuning at default settings | Keep tuning page-segmentation modes | The scan is the lowest-authority file and copies a source we already hold cleanly. No layout mode recovered its price table | Some text is lost | Image-only documents become a main source |
| 013 | 2026-11-12 | One `Record` contract between loading and chunking | Let each loader hand chunking its own shape | Later steps never need to know the original format. A new format needs only a new loader | One more layer to keep consistent | Records become too large to hold in memory |
| 014 | 2026-11-12 | Report near-duplicates, never delete them | Delete near-duplicates | Similarity cannot tell the current version from an old one. The manifest decides | Related files stay, so the status filter must be reliable | The corpus grows past a few thousand documents; then use a faster matching method |
| 015 | 2026-11-13 | One clause is one chunk, and the clause ID comes from the document's own numbering | Fixed-size chunks | Sharp matches, and every chunk is a citable unit that stays stable across edits | Depends on documents being numbered; unnumbered ones fall back to paragraphs | Most customer documents arrive unnumbered |
| 016 | 2026-11-13 | OCR text never receives a clause ID | Accept IDs read by OCR | An ID read by OCR can be wrong and would look real in the registry | OCR content cannot be cited by number | OCR output can be checked automatically against a clean source |
| 017 | 2026-11-13 | Price tables are kept out of the vector index; prices come only from `plans_fees` | Embed the price table text with the rest | One source of truth for every price | Price text in documents must be cut before chunking | A pricing service replaces the table |
| 018 | 2026-11-13 | Route by data type with plain rules first | Model-based router from the start | Free, instant, deterministic and easy to test | Brittle on unusual phrasing; a model-based router can be compared later with the same tests | A model-based router beats the rules on the golden set. Routing is revised by 021 |
| 019 | 2026-11-13 | Apply the status filter inside the SQL query, before ranking (refines 004) | Filter after retrieval in code; rely on the verifier alone | Similarity cannot tell an approved clause from a superseded one, so unofficial text should never reach the model | The vector index filters after searching, so on a large table a strict filter can return too few rows | The table grows large enough to partition by status or over-fetch |
| 020 | 2026-11-13 | Verify citations in code, not with a model | Ask a model to check its own answer | Deterministic, free and independent of the answering model's blind spots | Proves where a citation came from, not that the clause supports the claim, so the judge is still needed | A cheap, reliable check that a clause supports the claim exists |
| 021 | 2026-11-13 | Add price rows to the vector results instead of substituting for them (revises the routing in 018) | Keep exclusive routing; train a classifier | A price word is a weak signal. Q06, Q15 and Q32 failed under exclusive routing | A longer prompt and slightly more cost per question | The extra rows lower answer quality on the golden set |
| 022 | 2026-11-13 | Store "not offered" cells as rows with a note, and allow a null price | Leave absent cells out; infer from missing rows | A fact can be an absence. Q12 had no evidence anywhere without it | Price is nullable, so every lookup must handle a row with no number | The pricing structure outgrows one table |
| 023 | 2026-11-13 | Score with two verdicts (code checks and a judge), two runs per question, and never overwrite the baseline | One verdict; one run; overwrite earlier results | Code and a judge fail differently, runs vary, and the before and after comparison needs the original | About 450 model calls and about an hour per full run, plus more result files | Run time or cost becomes a barrier, or the judge model changes |
